## 实际调用链

`DataLocationsPanel → preload.dataLocations → registerDataLocationsIpc → shell.openPath`。共享契约只有零参数 `read()` 和接受 `data | backups | logs` 的 `open(target)`。主进程仍严格验证调用来源、主 frame、页面 URL 和入参，不接受任何用户提供的路径、URL、SQL 或文件内容请求。

位置来自本进程已经设置的 `app.getPath('userData')`，输出数据目录、保护备份目录、日志目录及 `application.log` 路径。读取只返回实际配置，不访问文件系统或数据库，不建立空目录。因而数据库不可用时仍可显示位置；`App` 错误状态复用同一面板，并保持练习/题库入口不可用。启动失败导致窗口无法打开时，原生错误提示包含实际数据与日志位置，未隐藏错误。

## 文件夹打开与错误

打开时解析当前数据根的真实路径。数据根本身必须存在，不递归重新建立；备份或日志子目录可以在用户点击时建立为空目录。确认目标为独立普通文件夹、没有子目录链接或规范化路径变化后才调用系统打开。目录文件冲突、junction、权限/文件系统错误、系统非空错误字符串与 Promise 拒绝均明确失败，可重新操作；错误日志使用固定描述，不记录系统返回的任意内容。

Windows 同一目录大小写不同仍是同一位置。使用平台相对路径关系判断规范化后是否仍为同一目录，并将真实路径交给系统，不能用字符串严格相等误拒 Logs/logs。实际检查进一步复现了既有备份链路中 Backups 和 Backup-Staging 的同类误判，保护目录、内部备份读取和暂存目录也作相同修正；链接、硬链接、运行库、伴随文件和事务/哈希保护保持。

使用本地固定 Electron 42.11.15 的 `shell.openPath`，空字符串表示调用成功，非空字符串表示失败；官方行为见[Electron shell 文档](https://www.electronjs.org/docs/latest/api/shell#shellopenpathpath)。窗口反馈采用“已请求打开”，没有把系统接口返回等同于文件管理器窗口人工验收。

## 生命周期与界面

只允许一个在途打开操作。每次文件系统等待之后重新检查可信来源、导航代次、暂停和关闭状态；旧页面即使再次返回同一 URL，也不能让晚到操作打开文件夹。导航、渲染销毁和关闭使在途任务失效，清理注销处理器及监听。

恢复前暂停目录接口并等待在途操作结算，然后再创建保护性备份和严格关闭业务连接。准备失败恢复入口；正常关闭同样等待已发起操作，不能把可能继续创建目录的任务遗留到数据库替换之后。没有另建数据库连接、迁移或保存逻辑。

窗口同步 ref 拦截重复点击，打开期间共享父级忙碌状态，禁用导航、显示保存和备份操作。读取失败保留错误供重试，不返回假造默认位置；切页卸载取消旧读取对界面的写入。长路径在面板内换行，不改变题干/代码块空白与滚动规则。
